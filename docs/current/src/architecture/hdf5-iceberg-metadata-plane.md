# HDF5 ↔ Iceberg Metadata Plane — Design (#42)

**Problem.** Dense OTel telemetry arrives as **read-only HDF5** on NFS or local object storage.
We need Apache Iceberg metadata over those datasets in **local S3-compatible storage, separate
from the data**, with any indexing co-located with the Iceberg layer — and the read path must be
**maximally Dask/datashader-efficient from day one**. Polaris ships into the air gap **later**
(disk constraints today), so the catalog needs a stepping stone that the Polaris future state
replaces **without invalidating anything**.

**Approach.** Two phases over one schema: a *pointer-table* pattern now (Iceberg tables that
describe and index the external HDF5), graduating toward the
[Iceberg File Format API](https://iceberg.apache.org/blog/apache-iceberg-file-format-api/)
(HDF5 as a first-class Iceberg data format) and Puffin-carried indexes when the ecosystem and our
stack (PyIceberg/Dask) support them.

---

## 1. Design laws

1. **Conservation (datasets are Layer A).** The HDF5 datasets are read-only and never mutated,
   moved, or co-located with anything we write. All writes land in the metadata plane.
2. **Rebuildability (metadata/index plane is Layer B).** Every table, index, and overview is
   derived from the datasets and can be regenerated by re-running the registration pipeline.
   Losing the metadata plane is an inconvenience, never data loss.
3. **Catalog-agnostic warehouse (the carry-forward guarantee).** An Iceberg table *is* its
   `metadata.json` + manifests + data files in the warehouse. A catalog only maps
   `namespace.table → current metadata location`. Therefore migrating the stepping-stone catalog
   to Polaris is a set of `register_table(identifier, metadata_location)` calls — **zero bytes in
   the warehouse change**. Everything built in phase 1 survives verbatim.
4. **Fidelity-first optimization.** The real files are **contiguous** (audited: no chunking, no
   compression). Every read-path optimization is validated against `--contiguous` synthetics —
   the layout-faithful mode — so day-one wins on generated data transfer to the real datasets.

## 2. Planes and layout

```
DATASET PLANE (read-only, conserved)          METADATA PLANE (local S3, rebuildable)
─────────────────────────────────────         ──────────────────────────────────────────────
nfs:///data/**.h5          (posix)            s3://<metadata-bucket-or-prefix>/  e.g. cyberphy-md/
s3://ro-datasets/**.h5     (object)             iceberg/warehouse/                ← the warehouse
        │                                          telemetry/hdf5_datasets/       (Arrow pointer table)
        │  referenced by URI +                     telemetry/hdf5_chunk_stats/    (pruning stats)
        │  fingerprint, never written              telemetry/overviews_l1/ _l2/   (raster pyramids)
        └────────────────────────────►          indexes/kerchunk/<fingerprint>.json  ← byte-range refs
                                                semantic/*.ttl                    ← DCAT/SHACL (not JSON-LD)
                                                catalog/                          ← stepping stone state
```

Lab generator default object keys (no Hive `key=value` path partitions):

```
s3://cyberphy/datasets/hdf5/cphy/cphy_<ISO>_<part>Z.h5
```

Time bounds and soft tags live in **file attrs + metadata tables** (Arrow / Iceberg), not directories.
Customer air-gap layouts use **layout adapters** (`product_prefix`, `flat_prefix`, custom) for discovery only.

- Access is uniformly **fsspec** (`file://` for NFS, `s3://` for object storage) — the index
  refs, the registration scan, and the Dask readers all use the same abstraction, so NFS vs
  object storage is a URI difference, not a code path.
- Separate buckets (or prefixes with distinct policies) for the RO dataset plane vs the metadata
  plane; in dev, two prefixes (`…/datasets/…` vs `…/cyberphy-md/…`) model this on one bucket.

## 3. Catalog: stepping stone → Polaris

| | **Stepping stone (day one)** | **Future state** |
|---|---|---|
| Catalog | **PyIceberg SQL catalog (SQLite)** on a hostPath/claimRef PV (the zarf-registry PV pattern) | **Apache Polaris** (REST), in the Zarf package |
| Footprint | ~0 (a `.db` file; PyIceberg wheels ride the existing image) | JVM server image + persistence — the current disk blocker |
| Writers | the registration pipeline (single writer — SQLite's constraint is our topology anyway) | any |
| Readers | the Navigator engine resolves datasets at session start (low-frequency); Dask workers never touch the catalog — they read data via the index refs | REST for all engines |
| Migration | — | `register_table()` every table into Polaris; flip one catalog URI in config. Warehouse untouched (law 3). |

Namespacing is chosen **now** to be Polaris-ready: `telemetry.*` tables under a single warehouse
root, no catalog-specific naming anywhere in the schema.

**Image delta for the stepping stone** (`requirements-airgap.txt`): `pyiceberg`, `h5py`,
`kerchunk`, `zarr` — MB-scale additions; `pyarrow`/`fsspec`/`s3fs`/`dask`/`datashader` are
already shipped.

## 4. The tables (one schema, both phases)

**`telemetry.hdf5_datasets`** — one row per registered dataset (the pointer table):

| column | notes |
|---|---|
| `dataset_uuid` | from the file's collection uuid attr — stable identity |
| `fingerprint` | the structural-audit fingerprint (depth/kind/attr-cardinality) — idempotency key |
| `uri`, `size_bytes`, `mtime` | where it lives in the dataset plane (never rewritten) |
| `layout` | `contiguous` \| `chunked` (drives the index strategy, §5) |
| `n_series`, `n_time`, `dtype` | the Values block geometry |
| `t_min_ns`, `t_max_ns` | time coverage (from Timestamps) — coarse temporal pruning |
| `ref_uri` | the kerchunk reference manifest in `indexes/` |
| `overview_levels` | which pyramid levels exist for this dataset |
| `registered_at`, `audit_json` | provenance; full structural audit blob |

**`telemetry.hdf5_chunk_stats`** — one row per *virtual chunk* (§5): `dataset_uuid`,
`series_lo/hi`, `t_lo/hi`, `vmin/vmax/mean/count`. This is the pruning layer — and it is shaped
like Iceberg column stats / a future Puffin blob, so it graduates rather than being replaced.

**`telemetry.overviews_l1/_l2`** — downsampled rasters (§6), real parquet-backed Iceberg tables:
`dataset_uuid`, `series_bin`, `t_bin`, `vmin/vmax/mean/count`. Snapshot-consistent with
registration (a dataset and its overviews land in one transactional window).

Iceberg snapshots double as the **arrival log**: each registration is an append; time travel
answers "what was visible yesterday".

## 5. The index layer — contiguous is the real case

Kerchunk reference manifests expose each dataset as a virtual Zarr array over byte ranges.
Two source layouts, one abstraction:

- **Chunked sources** (our synthetic default): refs are the native HDF5 chunk map. Viewport →
  the chunks it covers → ranged GETs. Straightforward.
- **Contiguous sources — the audited real layout**: there is no chunk map, but row-major order
  makes byte offsets computable. We define a **virtual chunk grid over the slowest axis**:
  series-blocks × full time extent, each virtual chunk a single contiguous byte run
  (`offset = series_lo × n_time × itemsize`, `length = block_rows × n_time × itemsize`).
  Series-range pruning is byte-level; **time-axis pruning cannot be byte-level on this layout**
  — it comes from `hdf5_chunk_stats` + the overviews instead (which is why those tables are not
  optional).

Consequences, stated plainly: (a) the reference-manifest generator must support both modes;
(b) `hdf5_chunk_stats` rows are computed against the *virtual* grid so pruning semantics are
identical across layouts; (c) all benchmarks that matter run against `--contiguous` synthetics.

## 6. Day-one Dask/datashader efficiency

Each optimization is tagged with how it carries forward to the Polaris/real-data state.

1. **Overview-first rendering (the headline win).** First paint reads *only* `overviews_l1`
   (a few MB regardless of dataset size) → datashader rasterizes instantly; full-resolution
   hyperslabs stream in on zoom via the index. Never rasterize full-res for a zoomed-out
   viewport. *Carries forward: overview tables are plane-resident parquet; Polaris just
   catalogs them.*
2. **Stats-pruned hyperslabs.** A viewport (series×time×value filter) consults
   `hdf5_chunk_stats` first; only intersecting virtual chunks are fetched. On contiguous
   layouts this is the *only* time pruning — it must be in the day-one path, not an
   afterthought. *Carries forward: the stats shape maps onto Iceberg column stats / Puffin.*
3. **Virtual chunk = Dask block, coalesced to task-sized units.** Map the ref grid 1:1 onto
   `dask.array` blocks, then coalesce series-blocks so tasks land in the ~10–100 MB sweet spot —
   the graph stays small (the `MAX_PARTITIONS≈200` lesson from the parquet explorer applies
   verbatim). *Carries forward: block planning reads the refs, not the file layout.*
4. **Filter-before-rasterize, always.** The existing Navigator discipline (viewport → hyperslab
   → datashader) — never materialize more than the viewport needs. Unchanged; now catalog-aware.
5. **fsspec block caching.** Workers cache hot byte ranges (`blockcache`/`simplecache`) keyed by
   `(uri, offset)`; NFS and S3 benefit identically. *Carries forward: fsspec sits under every
   phase.*
6. **Persistent Dask sessions.** Already the architecture — the cluster holds the ref manifests
   and file handles warm across viewport interactions.

## 7. Read path (sequence)

```
engine session start ─► catalog: SELECT * FROM telemetry.hdf5_datasets [stepping stone: SQLite;
                                                                        future: Polaris REST]
viewport (RangeXY) ───► overviews_l1/_l2 → instant datashader raster        (first paint)
                   └──► hdf5_chunk_stats → surviving virtual chunks
                        └► kerchunk refs → ranged reads (fsspec file://|s3://)
                           └► dask.array blocks → hyperslab → datashader     (full res)
```

## 8. Registration pipeline (convergent, like everything else)

`scan → fingerprint → register → index → overview`, idempotent and re-runnable:

- **detect**: dataset URIs under the roots vs `hdf5_datasets` rows (keyed
  `dataset_uuid` + `fingerprint`; unchanged files are no-ops — the converge discipline).
- **remediate**: for new/changed datasets — structural audit (the existing h5audit
  fingerprinting), emit the reference manifest (mode per `layout`), compute
  `hdf5_chunk_stats` + overview pyramids (a Dask job over the virtual grid — the pipeline
  *uses* the read path it serves), append rows.
- Never writes to the dataset plane; a failed run re-converges.

## 9. Dev rig & validation gates

- **Rig**: devenv MinIO with two buckets (`ro-datasets` + metadata) and a local directory as the
  NFS stand-in; synthetics from `generate_hdf5.py` in **both** `--contiguous` (fidelity) and
  chunked (native-ref) modes; laptop k3d / devenv for the engine+Dask loop.
- **Gates**:
  1. registration idempotency (second run = all no-ops);
  2. byte-identical hyperslab results across `file://` vs `s3://` and contiguous vs chunked;
  3. first-paint latency budget met from overviews alone on a full-size contiguous synthetic;
  4. pruning effectiveness: bytes fetched for a 1% viewport ≪ full scan (measured, recorded);
  5. **catalog swap rehearsal**: `register_table` every table into a scratch Polaris (devenv has
     one) and re-run gates 2–4 with only the catalog URI changed — proving law 3 before we ever
     rely on it in the air gap.

## 10. Graduation path

1. **Polaris in the package** (when disk allows): add the component, run the registration
   `register_table` migration, flip the catalog URI. Nothing else moves.
2. **File Format API**: when a HDF5 `FileFormat` exists for our engines, `hdf5_datasets` rows
   become true Iceberg data-file entries; the pointer table remains as provenance.
3. **Puffin**: `hdf5_chunk_stats` content moves into snapshot-attached blobs; the table remains
   the human-queryable view.

## 11. Decisions

**Resolved here:** SQLite PyIceberg catalog on a hostPath PV as the stepping stone (single-writer
matches our topology; ~zero disk); kerchunk JSON refs keyed by fingerprint (revisit parquet-refs
only if manifests exceed ~50 MB); overviews as Iceberg parquet tables (not loose arrays) for
snapshot consistency; virtual series-block grid over contiguous sources with stats-based time
pruning; `telemetry.*` namespace.

**Open (to resolve during #43):** virtual block size default (start: rows ≈ 8 MB per block,
coalesce to ~64 MB tasks; tune on the contiguous synthetic); overview level policy (L1 fixed
~2000×1000 bins; L2 only for datasets over a size threshold); whether the engine caches the
SQLite catalog file locally per session or reads via the PV mount.
